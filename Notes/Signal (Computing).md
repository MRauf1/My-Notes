# Definition
> [!info] Signal (Computing)[^1]
> A software interrupt: when a process receives a signal, it stops executing its current program and responds to the signal instead.

# Properties
- On receipt, execution jumps from the currently executing line to a signal handler; if the process supplies no handler, a default handler runs instead, such as terminating or ignoring the signal.[^2]
- Has a four-stage life cycle: generated (a process raises it), pending (the kernel is about to deliver it), blocked (delivery is withheld), and received (the kernel delivers it) — each transition takes some nonzero time to complete.[^3]
- Considered poor practice as a mechanism for program logic, since a signal carries no guaranteed time frame or assurance of delivery; other means of communicating between [[Process (Computing)|processes]] are preferred for that purpose.[^4]
- `SIGSTOP` and `SIGCONT` pause and resume a process, respectively; a [[User Space Scheduler]] can use them to schedule a fixed list of commands itself.[^5]
- Convenient for delivering low-priority information and letting a user interact with a program when other channels don't work — for example, when standard input is frozen — and for letting a program clean up or otherwise react to an event; a program may also simply choose to ignore a signal.[^6]
- Because a program that handles signals well is tricky to write correctly, signals are generally reserved for termination and cleanup rather than built into ordinary program logic.[^6]
- Distinct from a hardware interrupt, which is generated directly by hardware and handled by the kernel because doing so requires elevated privilege; a signal is instead a software interrupt generated by the kernel, though it can still be generated in response to a hardware event, such as `SIGSEGV`.[^7]
